# Security and privacy

- POS users may read and edit evidence only for refund orders whose native `pos.order.user_id` is their Odoo user and whose company is allowed. This may be a shared POS login, not an identified individual cashier. POS managers may read and edit all evidence cases in their allowed companies. Record rules apply to searches, direct reads, exports and object actions.
- Ordinary users cannot create or delete cases. Only the internal native refund persistence hooks create cases with elevated privilege. SQL enforces one case per refund order. Direct case writes can change only reason and condition; server code sets evidence author and capture time. Manager note is restricted to POS managers.
- Reason codes are company-scoped. POS users may read; POS managers maintain them. Create and write explicitly validate the target company, including direct RPC moves; a used reason cannot move to another company. A case cannot accept an inactive or foreign-company reason. Company record rules still apply to direct RPC.
- No attachments, public route, controller, telemetry or external network request are added. Do not put personal data in condition notes. The module does not copy POS customer fields to its case model.
- A user's access is based on `pos.order.user_id`, not `pos.session.user_id`; the latter may be a session opener. Changes to the native order user can change case visibility. POS managers should supervise native order permissions, which Odoo grants to POS users.
- Unverified: Enterprise-specific extensions and cross-version Odoo 19 upgrades. Pinned Community source and lifecycle evidence are recorded in the release ledger.
- This is an operational review queue, not a tamper-evident ledger. The native POS order ACL can permit order deletion, which cascades to its case, and authorized users can revise reason/condition. Managers who need formal retention or change history should enforce that separately through their Odoo policy.
